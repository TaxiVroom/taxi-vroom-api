writeViaRepo|HARD: every write that can raise a domain event goes through repo.insert / repo.delete, or a repository's own save()-style method built on this.client.<model>.update(...) or .upsert(...) (PrismaRepositoryBase has no generic update; see ride.repository.ts save()), wrapped in repo.transaction(...), single-entity writes like a delete included (delete-user.service.ts skips it: a known bug, do not copy). Never call PrismaService or the Prisma client from a service. Inside a repository always read through the this.client getter (src/libs/db/prisma-repository.base.ts), never inject PrismaService there: this.client returns the ambient transaction connection. The connection travels per request through RequestContextService, not as a parameter: await every call inside the transaction() callback all the way down, or the write silently falls back to a non-transactional connection with no error. deps:validate catches none of this (nothing forbids application → infrastructure imports)
sameCommand|HARD: a new entry point for an existing use case (another HTTP endpoint, CLI, GraphQL, message pattern) builds and dispatches the same *.command.ts: see create-user.http.controller.ts, create-user.cli.controller.ts and create-user.message.controller.ts, which dispatch the identical CreateUserCommand. Never re-implement the use case's logic in the new adapter
repoPorts|HARD: repositories are injected by their port (interface) and DI token, @Inject(X_REPOSITORY) from <module>.di-tokens.ts, never the concrete class
eventsFromEntity|HARD: domain events are added inside the entity (this.addEvent(...)) and published only by AggregateRoot.publishEvents(), called from the repository after a successful write. Never call eventEmitter.emit() or .emitAsync() by hand from a service
logicInEntity|HARD: business logic and state transitions live in the entity or value objects (validate(), methods like user.makeAdmin()), not in the *.service.ts handler. A handler reads as: build or load the entity, call one or more entity methods, save via the repository. An if that decides a business outcome inside a handler means that logic belongs in the entity
resultInEntity|An expected, recoverable business failure returns Result<T, E> from the entity method itself (WalletEntity.withdraw() returns Err(new WalletNotEnoughBalanceError()) on insufficient balance) and the caller decides what to do. Throwing from validate() is reserved for invariants that should never happen (state corruption), not for normal business outcomes
shortMethods|Keep methods under about 30 lines: split out a private method when one grows past that
crossModule|Modules talk by domain events by default: addEvent() in the emitting module, @OnEvent in application/event-handlers/ of the listening one, the emitter never knows who listens (see create-wallet-when-user-is-created.domain-event-handler.ts). Two direct couplings are allowed, judged case by case and not limited to pre-approved situations: dispatching another module's own Command through commandBus.execute(...) (validate-registration-document.admin.http.controller.ts dispatches registration's command from admin), and a Request DTO extending another module's Request DTO. Never import another module's Entity, Repository or Command/Query handler class: only Command/Query classes and Request DTOs may be reused directly
responseWhitelist|Response DTOs whitelist their fields explicitly, as <module>.mapper.ts toResponse() does. Never return entity.getProps() or the entity itself
businessErrors|New business errors extend ExceptionBase and live in domain/<module>.errors.ts, with a code namespaced MODULE.REASON (USER.ALREADY_EXISTS), distinct from the GENERIC.* exceptions of libs/exceptions/. A command handler catches the generic technical exception (ConflictException from the repository) and translates it into the specific business error it returns as Err(...)
cqrsRead|HARD: the read flow bypasses domain and repository: a *.query-handler.ts injects PrismaService (@libs/db/prisma.service.ts) and queries through the generated client, mapping to a plain read model itself (find-users.query-handler.ts, get-boarding-code.query-handler.ts). Deliberate CQRS: never add an entity or repository call to a query, even when a repository method like findOneById covers the same lookup (it couples the query to what the write side later needs and returns a full entity instead of a lean read shape); write the query's own Prisma query, a trivial findMany/findUnique is not the duplication DRY is about. get-registration-document-url.query-handler.ts still injects repository ports: do not copy it
