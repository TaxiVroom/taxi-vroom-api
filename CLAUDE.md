# Working with the user

Never run `npm` commands yourself (`npm run ...`, `npm install`, `npx prisma ...`, etc.) — give the exact command as text and wait for the user to run it and paste back the result before continuing or drawing conclusions from it. Other shell commands (git, file inspection, etc.) are fine to run directly. Exception: `npx tsc --noEmit` and `npm run lint` are run directly, without asking.

# Commands

- `npm run start:dev` — dev server, hot reload.
- `npm run test` — unit tests (Jest). `npm run test:e2e` — e2e tests, requires: `npm run docker:env` then `npm run db:push:tests` (re-run `db:push:tests` after any `prisma/schema.prisma` change to keep the test DB in sync) **and** `npm run firebase:emulator` running in a separate terminal (Firebase Auth Emulator on port 9099 — `firebase-admin` calls in tests hit this instead of real Firebase; `jestGlobalSetup.ts` refuses to run without `FIREBASE_AUTH_EMULATOR_HOST` set, same spirit as its `DB_NAME` guard). `.env.test` holds placeholder `FIREBASE_*` values that are never actually used — `firebase-admin.service.ts` skips `credential.cert()` entirely when the emulator var is set. Use `tests/test-utils/fake-firebase-user.ts` (`createTestFirebaseUser`/`deleteAllTestFirebaseUsers`) to get a real ID token for a test user instead of calling Firebase for real.
- `npm run test:watch` and `npm run test:cov` are broken: they omit `--config .jestrc.json`, so they silently fall back to the incompatible `jest` block at the bottom of `package.json` (no path-alias resolution) and fail with unrelated `Cannot find module '@modules/...'` errors. To iterate on a single test, run `npx jest --config .jestrc.json --watch <path>` instead.
- `npm run lint` — eslint --fix.
- `npm run deps:validate` — checks the architecture boundaries below via `.dependency-cruiser.js`. Run it after adding or moving a file across domain/application/infrastructure/api — a wrong import direction fails this even when `tsc` is happy.
- Prisma, not Slonik: schema + migrations live in `prisma/` (`prisma/schema.prisma`, `prisma/migrations/`), not `database/`. `npm run migration:dev --name X` creates and applies a dev migration; `npm run migration:deploy` applies pending migrations (production); `npm run migration:reset[:tests]` drops, recreates and remigrates; `npm run migration:status` checks status; `npm run db:push[:tests]` pushes the schema without a migration file (used to sync the test DB); `npm run prisma:generate` regenerates the client; `npm run prisma:studio` opens the Prisma data browser.
- After `migration:dev`, run `npm run prisma:generate`: since Prisma 7, `migrate dev` no longer regenerates the client. `tsc` won't catch a stale client: `PrismaRepositoryBase.client` is typed `any`.
- DB env vars: `.env.example` (DB_HOST, DB_PORT, DB_USERNAME, DB_PASSWORD, DB_NAME).

# Architecture: DDD Hexagonal + CQRS

Write flow: route (`src/configs/app.routes.ts`) → `*.http.controller.ts` (builds a `*.command.ts`, calls `commandBus.execute()`) → `*.service.ts` (`@CommandHandler`) → `domain/*.entity.ts` (business rules, raises events via `this.addEvent(...)`) → `database/*.repository.ts` (`extends PrismaRepositoryBase`, write wrapped in `repo.transaction(...)`) → event published → `application/event-handlers/*.domain-event-handler.ts` (`@OnEvent`, may live in a different module).

Read flow bypasses domain and repository entirely: `*.query-handler.ts` injects `PrismaService` (`@libs/db/prisma.service.ts`) directly and queries via the generated client, mapping the result to a plain read model itself — see `find-vehicles.query-handler.ts` or `find-monthly-budget.query-handler.ts`. This is deliberate CQRS — don't "fix" it by adding an entity or repository call to a query, even when a repository method like `findOneById` already covers the same lookup: reusing it couples the query to whatever the write side later needs and returns a full entity instead of a lean read shape. Write the query's own Prisma query instead — a trivial `findMany`/`findUnique` isn't the kind of duplication DRY is about. No exception: every `*.query-handler.ts` in this codebase already follows this, including `find-debts`, `find-contacts`, `find-recurring-charges` and `find-monthly-budgets`, which used to inject a repository port — don't reintroduce that pattern.

`npm run deps:validate` already enforces, and will fail the build on: `domain/` importing api/application/infrastructure paths, infrastructure importing api paths, commands/queries importing api paths. Don't re-litigate those — but it does **not** catch the rules below, so nothing stops you from writing code that violates them silently:

- IMPORTANT: every write that can raise a domain event must go through `repo.insert`/`repo.delete`, or a repository's own custom `save()`-style method built on `this.client.<model>.update(...)` (see `debt.repository.ts`'s `save()` — `PrismaRepositoryBase` has no generic `update`, since Prisma's update shape differs per aggregate) — wrapped in `repo.transaction(...)`, including single-entity writes like a delete (`delete-user.service.ts` in this codebase skips this and is a known bug, don't copy that pattern). Never call `PrismaService`/the Prisma client directly from a service. Inside a repository, always read through the `this.client` getter (`@libs/db/prisma-repository.base.ts`), never inject `PrismaService` and call it directly — `this.client` returns the ambient transaction connection when one is open. The transaction connection is propagated implicitly per request via `RequestContextService` (not passed as a parameter) — `await` every call inside the `transaction()` callback all the way down, or the write silently falls back to a non-transactional connection with no error. `deps:validate` will not catch any of this (nothing forbids application → infrastructure imports).
- A new entry point for an existing use case (a different HTTP endpoint, CLI, GraphQL, message pattern...) builds and dispatches the *same* `*.command.ts` — see `create-lent-debt.http.controller.ts` and `create-borrowed-debt.http.controller.ts`, which take different Request DTOs (lender-facing vs. borrower-facing) but both construct and dispatch the identical `CreateDebtCommand`. Never re-implement the use case's logic inside the new adapter.
- Repositories are injected via their port/interface + DI token (`@Inject(X_REPOSITORY)` from `<module>.di-tokens.ts`), never the concrete class.
- Domain events are added inside the entity (`this.addEvent(...)`) and published only by `AggregateRoot.publishEvents()`, called from the repository after a successful write. Never call `eventEmitter.emit()` / `.emitAsync()` manually from a service.
- Business logic and state transitions belong in the entity/value objects (`validate()`, methods like `user.makeAdmin()`), not in the `*.service.ts` handler. A handler should read as: build or load the entity → call one or more entity methods → save via repo. An `if` deciding a business outcome inside a handler is a sign that logic should move into the entity.
- Keep methods under ~30 lines; split out a private method when one grows past that.
- Inside an entity, an expected/recoverable business failure returns `Result<T, E>` from the method itself (e.g. `WalletEntity.withdraw()` returns `Err(new WalletNotEnoughBalanceError())` on insufficient balance) — the caller decides what to do with it. Reserve throwing from `validate()` for invariants that should never happen (state corruption), not for normal business outcomes.
- Cross-module communication defaults to Domain Events (`addEvent()` in the emitting module + `@OnEvent` in `application/event-handlers/` of the listening module) — the emitting module never knows who, if anyone, is listening. Two direct-coupling mechanisms are also allowed, judged case by case (not restricted to specific pre-approved situations): (1) dispatching another module's own Command via `commandBus.execute(...)` instead of waiting on an event; (2) a Request DTO extending another module's Request DTO. Current example of both: `account`/`contact` will dispatch `user`'s `CreateUserCommand` directly (wrapped in their own `repo.transaction(...)`) to create the shared CTI base `User` row, and their Request DTOs will extend the shared identity fields (`firstName`, `lastName`, later `phone`) defined in `src/modules/user/commands/create-user/create-user.command.ts` (marked `// TODO: move to libs, used by multiple modules` — stays there for now). Still never import another module's Entity, Repository, or Command/Query Handler class directly — only Command/Query classes and Request DTOs are fair game for direct cross-module reuse.
- Response DTOs whitelist fields explicitly, the way `<module>.mapper.ts`'s `toResponse()` does. Never return `entity.getProps()` or the entity itself.
- New business errors extend `ExceptionBase` and live in `domain/<module>.errors.ts`, with `code` namespaced as `MODULE.REASON` (e.g. `USER.ALREADY_EXISTS`) — distinct from the generic `GENERIC.*` exceptions in `libs/exceptions/`. A command handler catches the generic technical exception (e.g. `ConflictException` from the repository) and translates it into the specific business error before returning `Err(...)`.

# Tests

e2e tests are Gherkin via `jest-cucumber`: one `<action>.feature` + one `<action>.e2e-spec.ts` per use case, under `tests/<module>/<action>/`, mirroring `src/modules/<module>/commands|queries/<action>/`. Follow that pairing for new use cases instead of a plain `.e2e-spec.ts`.

IMPORTANT: e2e tests run against a real Postgres database and `TRUNCATE` tables between scenarios (see any `*.e2e-spec.ts`'s `afterEach`). `tests/setup/jestGlobalSetup.ts` refuses to run unless `DB_NAME` contains the word "test" (`.env.test` uses `ddh_tests`) — never weaken or remove that check, it's the only thing preventing e2e tests from wiping a non-test database if env config is ever wrong.
